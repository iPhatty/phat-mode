# Repair is its own task kind, its state lives in markers on the pull request, and human actions stop it

Once phat-mode opened a pull request, it used to stop working on it. A PR that conflicted with its base branch after another PR merged, or that GitHub would not merge until it was updated, just sat there, and while it sat there `watch` built nothing else in that repo. phat-mode now **repairs** its own stuck pull requests, and hands one to a human only as a last resort.

**Its own task kind.** Repair is a third durable task (`phat.repair`), next to building (`phat.pipeline`) and shaping (`phat.shape`), with the same patterns: a checkpoint per phase, fixed request IDs, `StepFailure` → `fail`, per-repo services, and run records keyed per issue, so `status`, `resume` and `abort` cover it and the lock file's "doing" names it (`doing #12 repair (update)`). Its phases are `look` (decide from GitHub); for failed checks `rerun` (rerun the failed GitHub Actions jobs once per head, then end waiting) or `gather` (check out the head, collect each failed job's log tail and every other failed check's name, description and link) and `diagnose` (a read-only agent judges the cause); `prepare` (post the repair comment, reset the issue's workspace to the PR's head, fresh conversations), then the build's own finishing steps (merge the base branch in, conflicts to the implementer, check, code review, verify, describe, publish), and `fail` → `give-up`. A repair is held to the same bar as the build because it runs the same code, not a copy: for conflicts it enters the shared steps at `update` with a flag that sends the work through check, review and verify even when nothing new was merged; for failed checks it enters at `implement`, with the failures and the diagnosis. Conversations are fresh: the implementer is given the spec, the PR's description, and the plan's silent decisions and the build's departures, read back from that description, so a repair never depends on a finished run's state still being there.

**State lives on the pull request, on GitHub** (as for yolo's verdict, ADR 0002), so `watch` works it out on each look and it survives losing phat-mode's home folder:

- one comment per repair, carrying `<!-- phat-mode:repair n=<k> sha=<head it repaired> cause=<conflicts|checks|not-clean> round=<r> -->` and its outcome. Posting it, upserted by its marker, is what counts the repair, so a crash and restart never counts or posts twice;
- a rerun comment per head whose failed Actions jobs repair reran, carrying `<!-- phat-mode:rerun sha=<head> -->`; written before the rerun, so a crash never reruns twice, and the head is never rerun again;
- a base-red comment when diagnose judged the failed checks base red or flaky, carrying `<!-- phat-mode:base-red head=<head> base=<base branch head> cause=<base-red|flaky> -->`: repair waits while the base branch's head is still that one;
- a summary comment when repair gives up, carrying `<!-- phat-mode:repair-gave-up round=<r> -->` and every attempt of that round with its cause and outcome.

Only comments posted by the `gh` user count: on a public repo anyone can post a marker. The budget (`limits.maxRepairs`, 3) counts the distinct head commits repaired since the last give-up, and a head commit is never repaired twice, so a repair that changed nothing is not repeated. The budget only applies to a PR that is actually stuck: a clean, green PR is never given up on. `round` keeps the comments of a fresh budget apart from the earlier ones on the same commit.

**Why a PR is stuck** is one pure decision from GitHub alone, like `yoloMerge`, in this order: not phat-mode's (not its branch, or no verdict marker) or a human pushed commits → leave it; a "changes requested" review submitted after phat-mode's last push → paused; `phat-mode:stuck` → leave it; then conflicts (or behind a base that must be up to date) → conflicts; verdict `not-clean` → not clean; checks running or the head not settled → wait; failed checks → failed checks; otherwise not stuck. For failed checks, a rerun asked for less than a minute ago, or a base-red marker for this head whose base is still the base branch's head, means wait; this comes before the budget, so a base-red PR is never given up on. The budget is then applied to the cause; for failed checks only once diagnose finds this change caused them, so the rerun and the diagnosis, which spend nothing, also run on the head the last allowed repair pushed. Every outcome has a one-line reason for `watch`'s waiting lines. Repair handles conflicts and failed checks; not clean is reported but waits as before.

**Human actions stop it.** Repair never overrides a human: commits a human pushed, a "changes requested" review after phat-mode's last push (a plain comment or an approval does not pause it), and the `phat-mode:stuck` label each leave the PR alone. That holds while a repair runs too: it checks again before it starts work, before each merge of the base branch, before publishing and before giving up (also after a resume; a give-up saves that it checked before it changes anything, so after an interruption only the stuck label it may have set itself is let through), and stops (without counting against the budget or labelling anything) when a human acted meanwhile. Its push is leased to the head it started from, never to whatever the clone last fetched, so a commit a human pushes even moments before is never overwritten. Giving up labels the PR `phat-mode:stuck` and fails the issue (`phat-mode:failed`, `ready-for-human`), like a failed build; only a human removes the label, which gives a fresh budget.

**Reruns and base-red checks don't count as attempts.** Only a diagnosis of `this-change` posts a repair comment. Rerunning failed GitHub Actions jobs once per head commit costs no agent run, and a failure that a rerun clears was never this change's. A check that also fails on the base branch, or is flaky, is someone else's breakage: repair waits, without spending an attempt, until the base branch moves on. A failure out of reach of any code change (secrets, external services, permissions) gives up at once instead, with the reason. Counting either would spend the budget on failures no change to this PR can fix, and give up on PRs that were fine.

## Considered Options

- **Repair inside the build pipeline** (more phases after publish). Rejected: a build run would stay open while CI runs and other PRs merge, holding the project's one slot for hours; and a repair starts later, from what is on GitHub, not from the build's state.
- **Counting repairs in the local durable database.** Rejected: it is lost with phat-mode's home folder and breaks `watch`'s rule of working everything out from GitHub on each look.
- **Counting with labels** (`phat-mode:repair-1`, …). Rejected: a label cannot carry the commit it repaired, so "never twice on the same commit" could not be told, and labels are easily edited by anyone triaging.
- **Overriding human changes** (repairing a PR with human commits, or under a "changes requested" review). Rejected: phat-mode must never push over a human's work or under their review.

## When to revisit

Revisit when a repair pushes over a human's work, when a PR is given up on that a repair could have fixed, or when GitHub's mergeability fields turn out not to say reliably when a PR conflicts or is behind.
