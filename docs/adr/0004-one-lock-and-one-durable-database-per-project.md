# One lock and one durable database per project

phat-mode keeps each project's runs in a Pi Durable database of its own (`state/<owner>__<name>.sqlite` in its home), protected by a lock of its own (`locks/<owner>__<name>.lock`). A process takes a project's lock before it opens that project's database, and keeps it until it has closed it. Pi Durable storage has no cross-process locking: two processes with one database open would both resume the same tasks and overwrite each other's commits. So a database must only ever be open in one process, and the lock is what guarantees it. With one lock and one database per project, different processes can work on different projects at once (a `watch` of one repo next to a `run` on another), while one project is only ever worked on by one process.

The lock file says who holds the project (pid, command, start time) and what it is doing right now (issue, build or shaping, phase), rewritten atomically as each phase starts and cleared when the run settles. That lets `status` report on a held project from its lock file, never opening its database. A lock whose process is gone is taken over, and no crash, at any point, can let two processes hold one: the lock is a folder of claims with unique names. A process puts its claim in, then lists the claims, and holds the lock only if no other claim belongs to a live process; otherwise it takes its claim out again (refused by a holder, or trying again shortly after another claimant). Of two that would both hold, the later one listed after the other's claim was in place, so it stepped back; a dead process's claim never counts. (Moving a stale lock file aside and taking its place, or numbering holders and taking the number after a dead one, both let two processes hold the lock when takeovers interleave or a process dies mid-way.) Writes to the Copilot `auth.json`, which every process shares, take a file lock of their own and re-read the file under it, so concurrent token refreshes never overwrite a newer token with an older one.

The single shared `state.sqlite` of earlier versions is retired once: archived to `state.sqlite.legacy` when it has no unfinished runs; otherwise phat-mode refuses to start (except `status`) and says to finish or abort them with the previous version. Runs are not migrated between databases: copying tasks, conversations and documents across Pi Durable stores is not supported, and finishing a handful of runs first is simpler and safer.

## Considered Options

- **One shared database with a finer lock** (per project, inside the one database). Rejected: the database would still be opened by two processes at once, which Pi Durable does not support, whatever the lock covers.
- **A daemon** that owns every database, with the CLI commands as its clients (as sketched in `docs/plans/web-dashboard.md`). Rejected for now: a long-running service to install and keep alive is much more than parallel projects need. Per-project databases do not rule it out later.
- **One lock for the whole home, as before.** Rejected: it keeps phat-mode to one process at a time, so starting work on another project means waiting for the current run or restarting `watch`.
